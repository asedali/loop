# M0.2 — Password reset + email verification

**Plan ref:** Adoption plan §2 / M0.2. Also the first item in the
`docs/TECHNICAL.md` §11 list that is still missing, and the prerequisite M4.4
(share links) gates on ("requires verified email").
**Attacks:** gap 7. Also removes the README's "a forgotten password is a manual
database edit".

## Problem

There is no way to recover a forgotten password. Today that means editing
`users.password_hash` by hand against the database, which means the only support
path for a real researcher involves the founder with production credentials.

There is also no way to establish that an email address belongs to the person who
signed up. That does not matter much *yet* — the only send path would be
password reset — but M4.4 (share links) and M5.1 (invite a co-founder) both
explicitly gate on a verified address, so the column has to exist before those
land rather than after.

## Change

### Schema

`users.email_verified_at` (nullable `timestamptz`).

One new table, `password_reset_tokens`:

| Column | Meaning |
|---|---|
| `user_id` | `ON DELETE CASCADE` |
| `purpose` | `password_reset` \| `email_verify` (constants + CHECK, invariant 2) |
| `token_hash` | SHA-256 hex, unique |
| `expires_at` | 30 minutes out by default |
| `used_at` | set on redemption — this is what makes a token single-use |

**One table, two purposes.** The plan names `password_reset_tokens`; email
verification needs exactly the same primitive (random token, hashed, expiring,
single-use), and a second near-identical table would be two sets of token-
rotation bugs to maintain. The `purpose` column keeps the two flows from ever
reading each other's tokens.

### Tokens

- 32 bytes from `secrets.token_urlsafe`, so the token is unguessable.
- Only the SHA-256 is stored. A database dump therefore does not hand over the
  ability to take over an account, and the comparison is `hmac.compare_digest`.
- `expires_at` is 30 minutes out (`PASSWORD_RESET_TOKEN_MINUTES`).
- Redemption sets `used_at`, and password reset additionally marks every other
  unused reset token for that user as used — a reset must not leave a second
  live token behind.
- **Not** invalidated by changing the password: there is no server-side session
  table (the session is a stateless signed cookie), so existing cookies cannot be
  revoked. Documented, not silently ignored — see Non-goals.

### Mail

New `app/mailer.py`, deliberately thin, with the backend chosen by
`MAIL_BACKEND`:

- `console` (default) — prints the message. This is what dev and the test suite
  use, and it is why the reset flow is testable without a provider or a network.
- `smtp` — `smtplib`, config from env.

`send()` never raises into a request. A mail failure must not 500 the signup
page, and the forgot-password response is identical whether or not the account
exists, so the user cannot tell a delivery failure from a wrong address anyway.

### Email confirmation is off by default

Added after the fact, and not to the design as written above.

`EMAIL_VERIFICATION_ENABLED` (default `0`) gates the confirmation half of this
milestone: the signup email, the banner, and `/resend-verification`. With the
flag on, everything below holds as originally specified.

It is off because `console` is the only backend configured anywhere in this
repo. A live confirmation flag on top of a console backend would put a permanent
banner on every account, asking it to click a link that is printed to stdout
instead of delivered — a worse experience than having no confirmation at all.

Two details fall out of disabling it:

- `/verify-email` stays mounted and still redeems. A link already sitting in
  someone's inbox must not rot because the flag was flipped afterwards.
- `db.user_is_verified()` returns `True` while the flag is off. Nothing gates on
  it yet, but M4.4 and M5.1 are meant to, and with confirmation disabled no
  account ever gets an `email_verified_at` — a plain column read would report
  every user as unverified and lock out the whole app when either ships.

Password reset is unaffected by the flag and still runs either way, though on
`console` its links are printed rather than delivered.

### Routes

| Route | Method | Notes |
|---|---|---|
| `/forgot-password` | GET/POST | POST → 303. **Neutral response**: the same message and the same redirect whether or not the address is registered |
| `/reset-password?token=…` | GET/POST | POST → 303. Validates, then sets the new password |
| `/verify-email?token=…` | GET | Confirms and stamps `email_verified_at`, then 303 |
| `/resend-verification` | POST | 303. From the unverified banner |

`/verify-email` is a GET because it is a link in an email: a third party cannot
trigger it without the token, and forcing a confirm click would add a step to
every single account. `/resend-verification` — the one a logged-in user triggers
deliberately — is a POST.

### Banner

Signed-in users with `email_verified_at IS NULL` see a dismissible-looking
banner in `base.html` with a resend button. The banner reads `user.email_verified_at`
off the row `render()` already puts in context, so it costs no per-page plumbing
and cannot drift between pages.

**The banner is not a gate.** An unverified account uses the whole app, exactly
as the plan requires. What it does *not* get is anything that sends mail to a
third party or publishes a venture — no such feature exists yet, so nothing is
gated today. `db.user_is_verified()` exists so M4.4 and M5.1 have one place to
ask.

### Login throttling

Two fixes, both named in the plan:

- **Key on IP as well as email.** One attacker spraying one password across
  thousands of addresses was previously invisible.
- **Clear on success.** Otherwise six typos in a row lock the account out for the
  rest of the window, which reads as the app being broken.

## Acceptance criteria

- [x] The reset flow works end to end against the console backend: request, read
      the link out of the mailer, redeem it, log in with the new password.
- [x] A token is single-use: a second redemption of the same link is refused.
- [x] An expired token is refused.
- [x] A tampered/unknown token is refused, and the refusal is indistinguishable
      from expiry to the user.
- [x] Only the hash is stored — no plaintext token in the database.
- [x] Redeeming a reset marks the user's other unused reset tokens used.
- [x] Unverified users can sign in and use the app, and see the banner. *(With
      `EMAIL_VERIFICATION_ENABLED=1`; the flag is off by default.)*
- [x] With the flag off, signup sends nothing, mints no token, shows no banner,
      and `/resend-verification` is a no-op that still requires a session.
- [x] `POST /forgot-password` reveals nothing about whether the address exists.
- [x] Login throttling keys on IP, and a successful login clears the history.
- [x] Migration is additive and nullable, so it applies to a live table with no
      backfill and no table rewrite.
- [x] `constants.py` and `schema.py` stay engine-free (invariant 7).
- [x] New POSTs all 303 (invariant 8); new form actions mirrored in
      `tests/test_frontend.py`.
- [x] Every page still works with JS disabled.

## Deliberate non-goals

- **Sessions are not invalidated by a password reset.** The session is a
  stateless signed cookie; there is no table to revoke against. Revocation needs
  a server-side session store and is a larger change than this slice.
- **No "you're already verified" branch.** Re-verifying a verified address is
  simply a no-op.
- **Existing users are left `email_verified_at = NULL`.** Backfilling to
  `created_at` would assert something that never happened. They get the banner.
- **No rate limiting on `/forgot-password` beyond the shared LLM limiter**, which
  does not cover it. It is not an LLM route. It is cheap and non-enumerating, but
  it does allow mail-bombing a known address. Worth revisiting with M2.6, when
  the mailer gains a real provider and a per-user send budget.
