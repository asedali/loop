# M0.7 — Changing your password actually signs the other sessions out

**Plan ref:** none available. The adoption plan is not in this repository. This
closes the security item in `docs/FLOW.md` §9 — "Changing a password does not
sign out existing sessions" — and the `Session` row in
`docs/TECHNICAL.md` §11.
**Attacks:** session theft. The one case where a stolen session cookie is
useless is immediately after the owner changes the password, and that is exactly
the case this app does not handle.

## Problem

Two problems, and the second is only visible once you fix the first.

**1. Nothing revokes a session.** The session is a stateless signed cookie with
no server-side table, so `get_current_user()` cannot tell a live session from one
issued before a password change. Changing the password is *the* moment a session
cookie stops being a credential — that is why people do it — and here it has no
effect on anyone already holding one.

**2. There is no way to change your password while signed in.** `set_password()`
has exactly one caller: the emailed reset flow. So "changing my password" is only
reachable by proving you own the inbox. A researcher who suspects a session was
stolen on a shared machine cannot rotate the credential without going to their
email first.

The exposure window is smaller than it looks, and stated so this is not
oversold: `SessionMiddleware` is configured with no `max_age`, so the cookie is a
**browser-session cookie** that dies when the browser closes. It does not sit on
disk indefinitely. The realistic cases are a machine left logged in, a profile
copied or exported, or an XSS that reads the cookie — none of which end when the
victim closes the browser.

## Change

### `users.session_epoch`, compared on every request

One integer column. The login flow writes the user's current epoch into the
cookie; `get_current_user()` compares it to the row it has *already loaded*.

The cost is **zero extra queries**, and that is why this shape was chosen over a
`sessions` table. `get_current_user()` already calls `db.get_user_by_id()` on
every request (it has to — it installs the RLS tenant from the row), so the
comparison is a field read on a row that is already in hand. A session table would
mean a new table, its own RLS policy, a cleanup job for expired rows, and a second
write on every request, to answer a question the user row can answer.

The epoch is **not a secret and does not need to be**. It is an integer anyone can
read from their own account row. All the security comes from the cookie still
being signed: forging one requires `SESSION_SECRET_KEY`. The epoch only decides
whether an *already-valid* cookie is still honoured — a revocation flag, not a
credential.

`db.set_password()` bumps the epoch itself rather than leaving it to callers.
That is the invariant worth having: it is not possible in this codebase to change
a password without revoking sessions, because the one function that does it is
the one function that advances the counter.

### A missing epoch is stale, deliberately

`get_current_user()` treats a cookie with no `session_epoch` as revoked rather
than assuming epoch 1. Assuming 1 would let precisely the cookies this change
exists to kill — the ones minted before the deploy — survive it.

The consequence, stated plainly: **deploying this signs everyone out once.** That
is the correct default for a security change and there is no way to avoid it
without a second mechanism; every existing session is, by definition, one issued
before password changes could revoke anything.

### Re-issuing your own session, and only your own

`POST /account/password` asks for the current password, exactly as
`/account/delete` does, because the whole point is to keep someone who has found
the session out from also changing the password. On success it re-issues the
*current* cookie with the new epoch and lets every other one die: the person
acting is not signed out of the tab they are acting in.

`auth.start_session()` is the single place that writes session keys, so login,
signup and password-change cannot drift apart on which keys a session carries.

### Not exported

`session_epoch` is added to `_EXPORT_EXCLUDED_COLUMNS`. It is not a credential,
so the reasoning that excludes `password_hash` does not apply — but it is
internal state of the session control, it tells the account holder nothing, and
exporting it invites the next person to treat it as a secret and rotate it. A
round-trip import resets it to 1, which is correct: imported rows get fresh
sessions.

## Acceptance criteria

- [x] Changing the password invalidates every other session immediately.
- [x] The session that performed the change keeps working.
- [x] A revoked cookie is treated as signed out on **every** route, not just the
      account page, and the RLS tenant is cleared on the way out.
- [x] A password reset also revokes existing sessions — that is the account
      takeover recovery path, and it is the case that matters most.
- [x] A cookie with no epoch (minted before the deploy) is refused.
- [x] Changing the password requires the current password; a wrong one changes
      nothing and says so.
- [x] Length limits are the same ones the reset flow enforces (min 8, max 72
      bytes), so the two paths cannot disagree.
- [x] `session_epoch` is absent from `/account/export`.
- [x] No new query per request beyond the user row that was already loaded.
- [x] Works with JS disabled.

## Non-goals

- **"Sign out of all my other devices" as a separate button.** It is the same
  operation as changing the password and there is no reason to offer a weaker
  version of a stronger one.
- **A session list, or per-device naming.** That is the `sessions` table, and the
  cost above is the reason it is not here.
- **Rotating `SESSION_SECRET_KEY`.** That would invalidate every session on every
  deploy. It belongs in a secret-rotation runbook, not in application code.
- **Revoking on email verification or logout.** Logout clears the caller's own
  cookie, which is the whole of what it can do; verification does not change a
  credential.
