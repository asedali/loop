# M0.3 — Per-request rate limiting on the LLM routes

**Plan ref:** Adoption plan §2 / M0.3. Also the third item named in
`docs/TECHNICAL.md` §11 ("if this goes in front of people you do not know, the
first three things to add are RLS, password reset, and per-request rate limiting
on the LLM routes").
**Attacks:** gap 7 (a privacy/security posture a researcher can defend), plus
the provider-cost guardrail in §4 of the plan.

## Problem

The monthly quota (`app/quota.py`) is a *budget*, not a *rate*. It bounds spend
per account per month and does nothing about a single user firing requests back
to back. Consequences today:

- One user can tie up a worker thread for the full duration of a slow provider
  call, repeatedly. `llm_timeout` is 60s and `LLM_MAX_ATTEMPTS` is 3.
- The provider sees the burst and 429s *us*, which surfaces to the user as
  "The AI provider is rate-limiting requests right now" — a message that blames
  the provider for something we could have prevented.
- A signup bot behind one IP spreads across many accounts and is invisible to a
  per-user budget entirely.

## Change

New module `app/ratelimit.py`: a **token bucket** per `(scope, key)` pair, held
in process memory.

- Scopes: `user:<id>` and `ip:<addr>`.
- Each scope has its own capacity and refill rate, both configured per minute
  (`LLM_RATE_LIMIT_PER_MIN`, `LLM_RATE_LIMIT_IP_PER_MIN`) over a shared window
  (`LLM_RATE_LIMIT_WINDOW_SECONDS`). Capacity == the per-minute number and refill
  is continuous, so a burst of N calls is allowed and call N+1 inside the window
  is refused, while a steady drip at the same average rate is not.
- `0` disables a scope.
- Oldest buckets are evicted when the map grows past `_MAX_BUCKETS`, so the
  in-memory map cannot be grown unboundedly by rotating source IPs.

Enforcement points, all five LLM-touching routes:

| Route | Check placement | Why there |
|---|---|---|
| `POST /phase1/extract` | before `quota.check` | nothing to save yet |
| `POST /venture/{id}/segment/{key}/run` | before `quota.check` | nothing to save yet |
| `POST /venture/{id}/run/{run_id}/log` | inside `_score_run`, **after** `log_cycle_results` | invariant 5: results must be persisted even if we refuse to score |
| `POST /venture/{id}/run/{run_id}/retry-analysis` | inside `_score_run` | results already on disk |
| `POST /venture/{id}/phase3/generate` | before `quota.check` | nothing to save yet |

Refusal renders `rate_limited.html` with status **429** and a `Retry-After`
header. It is a page, not a redirect: the user gets an explanation and a way
back rather than a silently-swallowed failure. It works with JS off (plain
response) and with JS on (`swapIn` replaces `<main>` and, because nothing
redirected, keeps the current URL so a POST endpoint never lands in the address
bar).

`ratelimit.reset()` exists for the test suite; `conftest.py` calls it from an
autouse fixture because the limiter is process-global and would otherwise leak
across tests.

## Known limitation (stated, not hidden)

The bucket is per **process**. Render's free plan is a single instance so this
matches the deployed topology, but a multi-instance deploy multiplies the
effective ceiling by the instance count. The quota remains the real budget; this
is a brake, not a security control. The module docstring says so too.

## Acceptance criteria

- [x] A burst of N rapid calls on one LLM route returns 429 with a friendly page.
- [x] **No `llm_calls` row is written for a rejected request** — the check runs
      before the model call, so a refusal cannot consume the caller's quota.
- [x] Existing quota behaviour is unchanged: `quota.check` still raises
      `QuotaExceeded` with the same message, and the two are independent.
- [x] The per-IP scope rejects even when the per-user scope still has tokens,
      and vice versa.
- [x] `/run/{id}/log` still saves the logged results when the verdict is refused.
- [x] Config values are runtime settings, read per call, with the usual
      degrade-to-default readers.
- [x] The page renders with JS disabled.

## Config

| Env var | Default | Meaning |
|---|---|---|
| `LLM_RATE_LIMIT_PER_MIN` | `12` | LLM requests per user per window. `0` disables the per-user scope. |
| `LLM_RATE_LIMIT_IP_PER_MIN` | `60` | LLM requests per IP per window. `0` disables the per-IP scope. |
| `LLM_RATE_LIMIT_WINDOW_SECONDS` | `60` | Window both scopes refill over. |
