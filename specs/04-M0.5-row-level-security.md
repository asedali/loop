# M0.5 — Row-level security

**Plan ref:** Adoption plan §2 / M0.5. The last item in the
`docs/TECHNICAL.md` §11 hardening list, and the one that closes the row that
currently reads **"Tenant isolation: `user_id` in every WHERE clause. No RLS. A
query bug is a data leak."**
**Attacks:** gap 7.

## Problem

Every lookup that takes an id also takes `user_id`, and that is load-bearing. But
it is load-bearing *by convention*: a single forgotten or mis-ordered `WHERE`
clause is a cross-tenant read, and nothing in the system would notice. For an
app whose users paste unpublished research and whose whole pitch is a private
record per person, that is the wrong thing to leave to review discipline.

RLS moves the guarantee out of the code and into the database: even a query with
no `user_id` filter at all cannot return another tenant's rows.

## Design

### The bypass problem, stated first

**RLS does nothing for a role with `BYPASSRLS`.** Postgres superusers bypass RLS
regardless of `FORCE ROW LEVEL SECURITY`, and so does Supabase's `service_role` —
which is exactly what `DATABASE_URL` points at today. So the policies below are
worthless unless the app connects as a role without that attribute.

The migration therefore creates `launchloop_app`
(`NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`) and grants it the table and
sequence privileges the app needs, and `get_conn()` switches to it with
`SET LOCAL ROLE`. Two safety properties, both deliberate:

- **Role creation is best-effort and never fatal.** A Supabase deploy where the
  migration role cannot `CREATE ROLE` still migrates cleanly; it just gets
  policies with no role to apply them. Failing the boot would be worse than
  running with a documented gap.
- **The role switch is conditional on membership.** `get_conn()` only issues
  `SET LOCAL ROLE launchloop_app` when `pg_has_role(current_user, …, 'member')`
  says it can. A deploy that has not granted membership keeps working exactly as
  before rather than 500-ing on every request.

`db.rls_active()` reports whether the policies are actually being enforced, and
`/healthz` surfaces it. **Claiming RLS while connected as a bypass role is the
exact overpromising the plan's guardrails warn about**, so the app is built to be
able to say out loud that it does not have it.

### Per-transaction tenant

A `ContextVar` holds the security context for the current transaction:
`user_id` plus `lookup_email` for the pre-authentication paths. `get_conn()`
issues the matching `SET LOCAL` statements.

Why a ContextVar and not a `user_id` parameter through all ~40 `db.py`
functions: a parameter can be forgotten at a call site, and a forgotten
parameter under RLS returns *zero rows* — which is a bug that hides. A ContextVar
set once per request in `auth.get_current_user()` cannot be forgotten at an
individual call site, and `get_current_user()` is already the single choke point
every route and every `render()` goes through.

**Safety of ContextVars across requests was verified, not assumed.** Starlette
runs sync handlers in a reused AnyIO worker thread, so a naive module global
would leak one tenant's identity into the next request. Probed directly
(`/tmp/probe_leak.py` pattern): anyio runs each task in a fresh
`copy_context()`, so a value set in one request is *not* visible in the next.
`TestTenantContextDoesNotLeak` keeps that property under test.

### Policies

| Table | Policy |
|---|---|
| `ideas`, `ventures`, `llm_calls`, `password_reset_tokens` | `user_id = app_user_id()` for all commands — they carry `user_id` directly |
| `bmc_elements`, `cycles`, `launch_strategy` | `EXISTS (SELECT 1 FROM ventures …)` — they carry `venture_id`, and referencing `ventures` costs no recursion because its policy does not refer back |
| `users` | SELECT on your own row **or** the single row matching `app.lookup_email` (login); INSERT only for the address being registered; UPDATE/DELETE only your own row |
| `login_attempts` | **not enabled** — see Non-goals |

All use `current_setting('app.user_id', true)`, so an unset tenant yields `NULL`,
`NULL = user_id` is `NULL`, and the row is not returned. **Unset means deny**:
the default is closed, not open.

`FORCE ROW LEVEL SECURITY` is applied so the policies bind the table owner too,
not just non-owners.

### `login_attempts` is deliberately excluded

It is the one table whose RLS would make a *security control* fail **open**.

Both throttling queries are pre-authentication, before any tenant is known, and
they are counted by `email` and by `ip`. If RLS filtered those rows by tenant,
every count would read zero, the lockout would never fire, and password guessing
would be *unlimited* — a silent regression that no test of the throttle's normal
path would catch. The table holds no research content and no secrets (an email,
an IP, a bool, a timestamp), so the protection would be worth nothing anyway.

This is a deliberate deviation from the plan's "for every table", recorded here
rather than quietly narrowed.

## Acceptance criteria

- [x] User B reads **0 rows** and writes affect **0 rows** for every RLS-enabled
      table, asserted table by table.
- [x] The 208 existing tests still pass, none of them weakened.
- [x] A user with **no** tenant set reads nothing (fail closed, not open).
- [x] `TestIsolation` is updated to switch tenants explicitly rather than rely on
      a default, so it keeps testing the query filters instead of passing
      vacuously because RLS returned nothing.
- [x] `db.rls_active()` is true under the test engine, and `/healthz` reports it.
- [x] Tenant context does not leak between requests in the same worker thread.
- [x] Role creation failing (no privilege) does not fail the migration.
- [x] `cycles` writes still work — the policy reaches through `ventures`, and
      `llm_calls` writes still work, so the quota still counts.
- [x] Migration is reversible; `login_attempts.ip` index is not disturbed.

## Non-goals

- **Not enabling RLS on `login_attempts`** (above).
- **Not a substitute for the `user_id` filters.** RLS is defence in depth; the
  existing `user_id` arguments stay, because `get_venture(id, user_id)` is what
  makes an unowned id bounce before it can reach the model and spend quota.
- **Not changing Supabase's grants.** Migration `a1c9f0e2b7d1` still revokes
  `anon`/`authenticated`. Membership in `launchloop_app` is a one-time manual
  step, documented in the README and `render.yaml`.
- **Indexing `user_id`.** RLS predicates on it, so on a large table it will want
  one. There is no large table yet; the existing indexes already lead with
  `user_id` or `venture_id`.
