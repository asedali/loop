# M0.4 — Auditability without storing prompt bodies

**Plan ref:** Adoption plan §2 / M0.4.
**Attacks:** gap 2 (a trustworthy evidence record) and gap 7 (a privacy posture
that can be defended). These pull in opposite directions on the surface; the
resolution is that the *identity* of a prompt is recorded and its *content* is
not.

## Problem

`llm_calls` records spend: purpose, provider, model, status, tokens, latency.
It does not record **which version of which prompt template** produced a result.
So when a prompt is edited — and prompts are the highest-churn code in this app,
because every output-validation rule in `docs/TECHNICAL.md` §5.3 exists because a
prompt was wrong once — there is no way to tell which historical results came
from the old template and which from the new one.

The naive fix, storing the prompt text, is unacceptable: prompts embed the
researcher's material verbatim inside the untrusted-data wrapper, so the column
would become a copy of unpublished IP in a table that outlives account deletion
(`llm_calls.user_id` is `ON DELETE SET NULL`).

## Change

Two nullable `Text` columns on `llm_calls`:

| Column | Content |
|---|---|
| `prompt_version` | a constant string per template, e.g. `analyze_segment_run.v1`, from `constants.PROMPT_VERSIONS` |
| `prompt_sha256` | lowercase hex SHA-256 of the exact prompt string sent, including the `wrap_key` envelope |

No prompt body is stored. Ever.

- `PROMPT_VERSIONS` lives in `app/constants.py` (engine-free, invariant 7) and
  is a **domain** constant, not config: it is telemetry about a code path, and a
  deployment must not be able to relabel history. Bumping a version string is a
  code change, deliberately reviewable.
- `prompt_sha256` is computed in `llm.call_json` over the prompt *as sent*, i.e.
  after the `wrap_key` envelope and before any retry corrective suffix — so the
  hash identifies the template instantiation, not a transient retry artefact.
- `_record()` gains two optional kwargs and writes them on both the success and
  the error path. `_record()` still swallows its own exceptions.

## Acceptance criteria

- [x] Every `llm_calls` row records `prompt_version` and `prompt_sha256`.
- [x] A unit test proves prompt bodies are never persisted: it drives a real
      `call_json` with distinctive material and asserts the string appears in no
      column of the logged row, and that `llm_calls` has no text column capable
      of holding one.
- [x] `prompt_sha256` is reproducible from the prompt string alone.
- [x] The error path records the version and hash too.
- [x] The migration is additive and nullable, so it applies to a production-shaped
      copy without a backfill.
- [x] `constants.py` and `schema.py` remain engine-free (invariant 7).
- [x] No new enum values, so no schema CHECK changes (invariant 2 is untouched).

## Non-goal

Retrieving a prompt by hash. That would require storing the body, which is the
thing being avoided. The hash answers "is this the same prompt I think it is",
not "what did it say".
