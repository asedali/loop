# M0.6 — Account data control

**Plan ref:** Adoption plan §2 / M0.6. Closes M0.
**Attacks:** gaps 2 and 7. A researcher cannot defend a privacy posture that has
no exit.

## Problem

Two absences, and they are the same absence.

There is no **download**. `pg_dump` is not a data-portability story: it hands a
researcher a dump of *everybody's* rows, and the only way to extract their own is
to be trusted with the database. For someone whose adoption criterion is "will
this app leak my unpublished IP", a manual database edit is not an answer.

There is no **delete**. M0.6's predecessors made account deletion *possible* by
accident — `users.id` is `ON DELETE CASCADE` almost everywhere — but nothing
exposes it. So "delete my account" is true in the schema and false in the
product, which is worse than either.

## Change

### `GET /account/export` — download my data

JSON, one document, `Content-Disposition: attachment`. Not a POST: it changes
nothing, so there is nothing for a cross-site request to cause, and a GET is
what a browser can download without JavaScript.

Shape is versioned and documented, and **flat** — arrays of rows with their ids
intact, so M4.3's round-trip (export, then re-import into a clean database) is
possible without inventing a nesting scheme now.

```
format        "launchloop.user_export.v1"
exported_at   ISO-8601
account       email, created_at, email_verified_at
ideas[]       the user's cards
ventures[]    their attempts
blocks[]      the nine-block canvas per venture
runs[]        one row per validation run, todos/results/analysis included
launch_strategies[]
llm_calls[]   purpose, provider, model, status, tokens, latency, month,
              prompt_version, prompt_sha256
```

Three deliberate exclusions:

| Excluded | Why |
|---|---|
| `users.password_hash` | obviously |
| `password_reset_tokens` | **entirely.** `token_hash` is a live credential for 30 minutes — an export that contains one is a takeover path, and it is the user's own row, so nobody would notice the leak |
| `llm_calls.error` | provider-supplied text. It is untrusted by invariant 9 and can quote request fragments back; the same reasoning as not storing prompt bodies (M0.4 §5.6) |

`llm_calls` is included rather than omitted on purpose: it is the user's own spend
and call history, and a "what did you do with my data" request that excluded it
would be incomplete. There are no prompt bodies in it to leak.

### `POST /account/delete` — delete my account

Hard delete of the `users` row; the cascades take `ideas`, `ventures`,
`bmc_elements`, `cycles`, `launch_strategy` and `password_reset_tokens` with it.
`llm_calls.user_id` is `SET NULL`, so spend and latency metadata outlives the
account while the content is gone.

Two gates, both deliberate for an irreversible action:

1. **Re-enter the password.** An unlocked laptop left on a desk should not be
   enough to destroy someone's research.
2. **Type `DELETE`.** Not a checkbox — a checkbox is one stray click, and this
   cannot be undone.

**Cascade under RLS was probed, not assumed.** PostgreSQL applies policies to
referential-integrity actions, and three of the child policies reach through a
`ventures` subquery whose parent row is being deleted. It works — RI triggers
execute with the table owner's rights — so no `BYPASSRLS` escape hatch is
needed, which is the outcome worth having: the deletion is authorised by the same
policies as everything else, rather than by a privileged back door.

The session is cleared and the user lands on `/login` with a note.

## Acceptance criteria

- [x] Deletion removes all user content; a test asserts **no orphan rows** in any
      table.
- [x] `llm_calls` rows survive with `user_id IS NULL`.
- [x] The export contains the user's data and no credentials.
- [x] The export respects tenant isolation: user B's download contains nothing of
      user A's.
- [x] Deletion requires the password, and the typed confirmation.
- [x] A wrong password deletes nothing.
- [x] The session is dead after deletion — the dashboard redirects to `/login`.
- [x] Download works with JS disabled.
- [x] The export is versioned, so M4.3 can change the shape without guessing.
- [x] Everything still works under row-level security, including the cascade.

## Non-goals

- **No CSV yet.** M4.3, alongside evidence and contacts, which is where CSV earns
  its keep.
- **No re-import.** M4.3 owns the round-trip test. The export is built flat and
  versioned so that re-import is additive rather than a re-shape.
- **No grace period or soft delete.** A hard delete is what the plan asks for and
  what the cascades already do correctly. If a recovery window is wanted later it
  belongs in `pg_dump`, not in the schema.
- **No email on deletion.** Nothing in this app sends mail for destructive
  actions, and a "we deleted your account" notice to an address that may be dead
  is not worth the plumbing.
- **No "download then offer to delete" nudge.** Two separate, unbundled buttons.
  Bundling them is how a data-export flow turns into a data-loss one.
