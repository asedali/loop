# M2.1 — Think like a founder: attributed playbooks as an adversarial mentor

**Plan ref:** none available. The adoption plan is not in this repository.
**Attacks:** the failure this whole app exists to prevent — a researcher talking
themselves past disconfirming evidence, helped along by a confident voice.

## Problem

Every other stage of this app pushes the researcher back onto their own evidence.
The kill-or-pivot decision is theirs (invariant 4). The verdicts are scored against
criteria they wrote. The action plan asks what *happened*.

Nothing in the app ever pushes back. A researcher whose Revenue block came back
`confirmed` on six friendly interviews gets no signal that six friendly interviews
is not a willingness-to-pay finding, and no signal either that their whole model
rests on one untested assumption.

That gap has an obvious, tempting, wrong filling: a "virtual Elon Musk" who tells
you your TAM is $50B. It fights the architecture on three fronts at once —
invariant 4 (the model does not dispose), the Phase 3 warning that a model "can
invent plausible-sounding ones", and the plain fact that it attributes invented
sentences to real and sometimes living people.

## Change

### A mentor that asks, and only asks

Six **playbooks**. Each is a real operator's *documented, published* operating
principle, used as an attribution label — never a person answering, never a quote,
never first person.

| key | Label | The principle |
|---|---|---|
| `focus` | Subtraction | Focus as subtraction; start from the customer experience and work backwards. Asks what you would delete |
| `first_principles` | First principles | Reason from constraints rather than precedent; delete parts rather than improve them. Asks what a thing actually costs |
| `demand` | Do things that don't scale | Manual, unscalable contact with users before automation. Asks who you have personally spoken to |
| `falsify` | Falsify the riskiest assumption | Build-measure-learn; attack the assumption that kills you if false. Asks which one it is |
| `jobs_to_be_done` | Demand, not features | The job the customer is hiring you for. Asks what changes in their day |
| `evidence` | The evidence insister | Not a person — this app's own thesis as a playbook. Asks what would disconfirm this |

`evidence` is deliberately in the set. The strongest version of this feature is
the one that turns the app's own standard against the researcher.

### The output shape makes assertion impossible

A prompt instruction is the kind of control that fails silently, so this is
structural, in four layers:

1. **There is no field for advice.** The response is
   `{questions: [{question, principle, why_it_matters}]}`. Nowhere for "your TAM
   is $50B" to go.
2. **A hard guard in `llm.py`.** Any question naming the person or speaking in
   first person is dropped. If nothing survives, raise `LLMError` — a visible
   failure beats a mentor talking in someone's voice.
3. **The prompt forbids** first person, quotes, and attribution of any statement
   to the person, and describes the persona as a principle being applied.
4. **The route writes only to `mentor_challenges`.** Nothing in the path calls
   `apply_verdict`, `set_segment_outcome` or `update_venture`, and a test asserts
   a challenge against a failed block leaves the outcome untouched.

This is a **security** control as much as a design one. Instructing a model to be
a more persuasive founder, inside a loop whose entire job is resisting
persuasion, is how you build a research tool that argues its user into a bad idea.

### The questions must be about *this* venture

The failure mode of every version of this feature I have seen is generic advice.
So the prompt carries the actual state: block outcomes and evidence notes, the
live hypothesis, logged outcomes with sample sizes, the action plan.

"Which of those six people told you they'd pay?" only exists because the prompt
knows the block was marked `confirmed` on six interviews that contained no
pricing question.

### Persisted, because the POST has to answer with a 303

Invariant 8. A stateless challenge would have to render in place and break it.

`mentor_challenges` carries `user_id` directly, so the RLS policy is the simple
`user_id = <tenant>` shape — not the `EXISTS over ventures` form — and the
nullable FKs cascade so a deleted idea or venture leaves no orphan.

### Quota parity

A challenge costs one call, counted and rate-limited exactly like the other four
purposes. Challenging your idea draws on the same budget as validating it, which
is a real tension and is stated rather than smoothed over: `quota.py`'s "500
covers roughly nine complete validations" is now slightly optimistic.

The `mentor_key` travels with each request rather than being saved. Arguing with
two playbooks on the same idea is the interesting use; "your mentor" is a product
decision this does not make.

## Acceptance criteria

- [x] Six playbooks, each naming a principle that operator has actually published.
- [x] Every challenge renders three to five questions, and never an answer.
- [x] A response naming the person or using first person is dropped, and a
      response of *only* such lines is a visible error rather than a persona.
- [x] A challenge cannot change a block's outcome, a run's verdict, or a venture's
      status — asserted, not assumed.
- [x] Reachable from Phase 1 (idea card), Phase 2 (a block) and Phase 3 (the plan).
- [x] Questions reference the specific logged evidence, not generic advice.
- [x] Tenant isolation holds: no challenge can be raised against another user's
      idea, block or venture, and none can be read.
- [x] It costs quota and obeys the rate limit like every other call.
- [x] Persisted, exported, and removed by account deletion.
- [x] Every challenge carries a persistent "AI-generated, not affiliated, not a
      quote" notice.
- [x] Works with JS disabled.

## Non-goals

- **No first person, ever.** Not even "Jobs would probably have…".
- **No invented quotes**, and no statement attributed to a person as theirs. Only
  principles they have actually published, named as attribution.
- **No free-form chat or conversation thread.** Each challenge is a
  self-contained card; there is no history to moderate and no state to carry.
- **No separate mentor budget** — see above, and the tension it creates.
- **No per-venture or per-day cap** beyond the per-request limiter and the monthly
  quota. A separate knob is a follow-up if the cost turns out to matter.
