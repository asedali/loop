# M3.1 — Marking action-plan steps done, with the outcome recorded

**Plan ref:** none available. The adoption plan is not in this repository; this
closes the first item in `docs/FLOW.md` §9 ("the action plan cannot be marked
done") and the last bullet in README's "leaves out".
**Attacks:** the funnel's dead end. Every other stage of this app ends somewhere
the researcher can act and record what happened. Phase 3 ends at a document.

## Problem

`launch_strategy.action_plan_json` is a read-only list. The app validates nine
blocks against real-world evidence, logs the results, forces a kill-or-pivot
decision when a critical block fails, and then hands over a sequenced plan — and
stops. The researcher ticks things off in a spreadsheet, or does not.

That is the one place where the product's own thesis does not apply. Everywhere
else, the loop's claim is "show me the evidence." Here the claim is "here is
what to do," and there is no place to record whether any of it happened. A plan
you cannot mark done is a document, not a loop.

## Change

### A real table, not a JSONB edit

`action_steps` gets one row per plan step. Two reasons this is not a
`completed: [true, false]` key added to the existing JSONB column:

- **The model regenerates.** `save_launch_strategy` *inserts* a new row and
  `get_launch_strategy` takes the newest, so "Regenerate strategy" already
  discards the old plan. Progress stored inside the strategy row would be
  destroyed by a button on the same page. Progress is the researcher's record of
  the real world; it outlives the model's opinion of what the plan should be.
- **It is exportable and countable.** `export_user_data` reads tables, and
  `delete_user_account` counts them, so a new table joins both for free. A new
  JSONB key would need to be threaded through both by hand.

### Identity is the step's own text, not its index

`position` alone cannot be the key. Regenerating the strategy produces a
*different* list, and index 3 of the new plan is not index 3 of the old one.
Keying on position would silently re-label a completion onto a step the
researcher never did — the exact class of bug this app is built to avoid.

So the natural key is `(venture_id, step_key)` where `step_key` is the SHA-256
of the step text. Same text → same key → completion survives regeneration. New
wording → new step → correctly not done. The uniqueness constraint is on that
pair, so a re-seed is an idempotent no-op rather than a duplicate.

The trade-off, stated: SHA-256 of the text means two steps with *identical*
wording share one row, so ticking one ticks both. That is the right behaviour —
they are the same instruction — and it is a real consequence of not inventing a
synthetic id the model never sees.

### Statuses: `pending`, `done`, `blocked`

Three, not one. A checkbox-only design forces a false choice, because the
realistic outcomes are "did it", "tried it, could not" and "not yet". `blocked`
is what makes the third answer recordable, and it is the one that carries the
most information — it is the thing worth looking at in three months.

`blocked` is deliberately **not** terminal. Un-blocking returns a step to
`pending` and keeps the note, because the note is why it was blocked and that
reason usually still holds.

### An outcome is required, not a checkbox

Marking a step `done` with no record of what happened is the failure mode this
app exists to prevent, so the route refuses an empty note for **both** `done` and
`blocked`, exactly as `park_segment` already refuses a park with no reason. The
copy says why, in the same voice: a completed step with no outcome is a claim,
and the claim is the thing the app was built to replace.

Reverting to `pending` needs no note — undoing is not an assertion.

### Nothing goes to the model

Marking a step done is a plain INSERT/UPDATE on a user-owned row. No LLM call,
so no quota cost and no rate-limit interaction; `throttle_llm` is deliberately
not called here. The consequence worth stating: a note recorded here is
researcher-authored text that has never been through the
`--- BEGIN UNTRUSTED DATA ---` wrapper, because nothing sends it to a model. If
a later slice feeds action-plan notes into a prompt, **that** wrapper becomes
mandatory — this table is the first place the app stores text the model has
never seen and might later be shown.

### Also fixed here: Phase 3 swallowed every LLM error

`venture_phase3.html` rendered no `{{ error }}` block, so `back_to_venture()`'s
`?err=` had nowhere to land. A provider outage or an exhausted quota during
"Generate launch strategy" redirected the user back to a page that looked
unchanged and said nothing — the exact swallowed-refusal failure
`back_to_venture`'s own docstring says it exists to prevent.

The phase3 render call also passed a hand-built context rather than `**ctx`, so
it was missing `error` and `note` even if the template had rendered them. Both
are fixed: the template gets the block, and the render passes `error=ctx["error"]`
and `note=ctx["note"]`.

This was found while scoping M3.1, not by a test failing — the existing suite
had no Phase 3 error-path test. It is the same shape as the swallowed import
failure fixed in M1.2, and the reason the invariant below is now asserted rather
than described.

## Acceptance criteria

- [x] Each plan step renders with its status, its note, and a control to change
      it.
- [x] `done` and `blocked` refuse an empty outcome note and say why, with a 303
      and no write.
- [x] A step's completion survives regenerating the strategy when the wording is
      unchanged, and does **not** carry over to a differently-worded step.
- [x] Reverting to `pending` keeps the note and clears the status.
- [x] One user cannot mark, read or revert another user's step — enforced by
      `venture_id` scoping in the route and by RLS underneath.
- [x] The page shows progress ("3 of 7 done") and a completed plan is visibly
      distinct from an untouched one.
- [x] Steps appear in `/account/export` and are removed by `/account/delete`.
- [x] No LLM call: marking a step spends no quota and touches no rate limiter.
- [x] Works with JS disabled; every control is a plain form POST.
- [x] Phase 3 now renders a provider error instead of swallowing it.

## Non-goals

- **No AI judge of the outcome.** A note saying "sent 40 emails, 6 replies" is
  the researcher's call. The app records it; it does not score it. The model
  already marked blocks, and invariant 4 says it does not dispose.
- **No per-step owner, due date, or reminder.** A task manager bolted onto the
  end of a validation loop is a different product, and none of it is what makes
  this loop close.
- **No reordering.** `docs/FLOW.md` §9 lists "no way to reorder or deprioritise
  the blocks" as a separate gap about the *canvas*, and inventing a second
  ordering concept for the plan would make two things called "order" mean
  different things.
- **No "plan is complete" venture status.** `VENTURE_STATUSES` has no such
  value, and the model does not get to declare a venture finished. A finished
  checklist is shown as progress, not promoted to a lifecycle state.
