# M1.1 — File upload with a preview before the AI call

**Plan ref:** Adoption plan §2 / M1.1.
**Attacks:** gap 3 and the funnel. A researcher should reach first idea cards in
under two minutes without writing a prompt — and right now that means finding a
plain-text file on disk.

## Problem

Phase 1 accepts one thing: pasted text. For most researchers the material they
have is a PDF — a thesis chapter, a paper, a preprint, a lab report. The current
path to getting that into the app is: open the PDF, select all, copy, paste,
clean up the headers and the reference list. That is the single largest drop-off
before the user has seen any value, and it is exactly the step a chatbot makes
trivial.

## Change

### No file is ever stored

`POST /phase1/upload` reads the upload into memory, parses it, and **discards
the bytes**. The extracted text comes back in an editable preview; the user trims
it and submits it as ordinary Phase 1 material.

This satisfies "delete the raw file by default" in the strongest available way —
the file is never written to disk in the first place. It also means there is no
upload directory, no cleanup job, no orphaned-file risk, and nothing to scan. The
preview round-trips through a form field, which is precisely what
`/phase1/new` already does with pasted text, so this slice adds no storage
concept at all.

M1.3's `materials` table can make it persistent later without changing this shape.

### Untrusted, like everything else

Extracted text is pasted text. It reaches `llm.extract_ideas` through the same
`--- BEGIN RESEARCHER MATERIAL (untrusted data) ---` wrapper, so a PDF containing
"ignore your instructions" is no more able to instruct the model than the same
sentence typed by hand.

### The upload surface

| Risk | Control |
|---|---|
| Huge body | `MAX_UPLOAD_BYTES`, default 8 MB. Read with an explicit cap rather than trusting `Content-Length`, and rejected while streaming |
| Wrong type | Magic-byte check on the actual bytes, *not* the browser's `Content-Type` or the filename extension — both are attacker-controlled |
| Decompression bomb | Page cap and a per-page deadline (below) |
| Path traversal | Never touches the filesystem, so there is no path to traverse |
| Malformed input | `app/upload.py` maps every parse failure to a plain-English sentence; no parser traceback reaches the user |
| Encrypted PDF | Detected (`is_encrypted`) and refused with an explanation, not a stack trace |
| Extracted-text flood | `MAX_EXTRACTED_CHARS`; a 900-page scan of someone's thesis does not become a 4 MB prompt |

### The timeout is a real deadline, not just a response deadline

`app/upload.py` takes a deadline and checks the clock **between PDF pages**, so a
pathologically slow document aborts mid-parse instead of tying up the worker.
This is deliberate: a thread in CPython **cannot be cancelled**, so a
`future.result(timeout=…)` bounds only the response, not the work. Checking per
page is the only way to actually stop `pypdf` — and `pypdf` is the parser that
decompresses content streams, so it is the one that matters. DOCX does not
decompress the same way and is bounded by the byte cap and entry count.

The residual risk, stated rather than hidden: a PDF engineered to be slow *per
page* can still consume up to the deadline. That is a bounded window, not an
unbounded one, and it is the honest limit of a same-process parse.

### Formats

| Format | Detection | Extraction |
|---|---|---|
| PDF | `%PDF-` | `pypdf`, page by page |
| DOCX | `PK\x03\x04` + `[Content_Types].xml` | `python-docx`, paragraphs + tables |
| TXT / MD | none (fallback) | decode with a byte cap; must look like text |

DOCX is a ZIP, so `PK\x03\x04` alone is not enough — the archive has to be
validated as an OOXML package, or any ZIP would be accepted and reported as a
Word document.

## Acceptance criteria

- [x] PDF, DOCX, TXT and MD each yield text.
- [x] A corrupt, oversized, empty or encrypted file gives a plain-English error
      and a 200, never a 500.
- [x] A file that is not the type it claims is refused.
- [x] Nothing is written to disk: the route returns no file handle and no path.
- [x] The preview arrives pre-filled and is editable, and submitting it is
      ordinary `POST /phase1/extract` — no new AI-call path, so no quota change.
- [x] Over-long extractions are truncated at a character cap.
- [x] The page cap is enforced and says so.
- [x] Works with JS disabled.
- [x] `python-multipart` was already a dependency, so no new upload machinery.

## Non-goals

- **No OCR.** A scanned PDF has no text layer; it gets a message saying exactly
  that, pointing at paste. Guessing would be worse than telling the truth.
- **No images, spreadsheets, or `.pages`/`.odt`.** Silent misparse into garbage is
  worse than a refusal.
- **No persistence.** M1.3.
- **No antivirus.** Not meaningful for the parse-only, discard-the-bytes
  posture above, and it would be a claim this app cannot make honestly.
